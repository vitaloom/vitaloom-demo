# VitaLoom Demo — API Contract v1

**Status:** Demo implementation contract  
**Daily timezone:** `Asia/Ho_Chi_Minh`  
**Timestamp format:** ISO 8601 with an explicit timezone offset. Producers should send UTC timestamps ending in `Z`.

This contract keeps the demo small while preserving clear business boundaries. Each metric has its own write endpoint and validation rules; the dashboard uses one read endpoint to retrieve all four metrics. This is a local demo contract, not a production API specification.

## 1. Conventions

- API paths use the `/api` prefix; Nginx forwards API requests to Spring Boot.
- JSON request and response bodies use `Content-Type: application/json`.
- `occurredAt` records when a measurement or user action happened. The backend adds `receivedAt` when it accepts an event.
- Keep raw events/records as the source of truth. Spring Boot is responsible for validation, persistence, and daily aggregation; clients and the producer must not calculate and submit authoritative daily totals.
- A missing metric is represented by `null`, not zero.
- For the MVP, a day starts at 00:00 in `Asia/Ho_Chi_Minh`. The backend derives the local statistics date from the original timestamp.
- Clients/producers create stable IDs for their own write records and must reuse the same ID when retrying that record.
- Spring Boot enforces uniqueness, backed by MongoDB unique indexes. Nginx does not create business IDs or decide whether a record is a duplicate.
- A retry with an already accepted ID must not create a second record or double-count the metric.
- Authentication and user-specific data isolation are not implemented in this local demo. Do not use this contract as a production multi-user API.

## 2. Health Check

### `GET /api/health`

Successful response — `200 OK`:

```json
{
  "status": "UP"
}
```

## 3. Daily Dashboard Statistics

### `GET /api/statistics/daily`

Returns all four metric values for the current date in `Asia/Ho_Chi_Minh`.

Successful response — `200 OK`:

```json
{
  "date": "2026-10-24",
  "timezone": "Asia/Ho_Chi_Minh",
  "heartRateBpm": 92,
  "steps": 1840,
  "sleepHours": 7.5,
  "waterMl": 1200
}
```

| Field | Type | Definition |
|---|---|---|
| `date` | string | Current local date, `YYYY-MM-DD` |
| `timezone` | string | Timezone used for the day's boundaries |
| `heartRateBpm` | number or `null` | Latest heart-rate measurement by `occurredAt` within the day |
| `steps` | integer or `null` | Sum of accepted step increments within the day; `null` if no step event exists |
| `sleepHours` | number or `null` | Sleep duration stored for the day |
| `waterMl` | integer or `null` | Sum of accepted water-intake records within the day; `null` if none exist |

The response is a read model. It may combine results from multiple metric-specific records; it does not imply the underlying metrics use the same write or processing logic.

## 4. Water Intake

### `POST /api/water-intakes`

Creates one water-intake record. Each drinking action is a separate record, and daily water intake is the sum of accepted records within the local day.

Request:

```json
{
  "intakeId": "intake-7a9f",
  "occurredAt": "2026-10-24T09:15:00+07:00",
  "amountMl": 250
}
```

Rules:

- `intakeId`: stable ID generated by the mobile client for this intake action. Reuse it if retrying the same action.
- `occurredAt`: time the water was consumed.
- `amountMl`: positive integer amount in millilitres. Reject zero/negative or implausible single-intake values (for example, above 5,000 mL).
- The backend stores each accepted intake record and derives the daily total from those records.
- A repeated `intakeId` must not be counted twice. A duplicate request should return a clear duplicate result or the original record without inserting another one.

Successful response — `201 Created`:

```json
{
  "intakeId": "intake-7a9f",
  "amountMl": 250,
  "status": "CREATED"
}
```

## 5. Sleep

### `PUT /api/sleep/daily`

Creates or replaces the current day's sleep-duration record. The demo supports one sleep record per local calendar day.

Request:

```json
{
  "sleepHours": 7.5
}
```

Rules:

- The backend determines the current date in `Asia/Ho_Chi_Minh`; clients do not supply a timezone-dependent date for the MVP.
- `sleepHours` must be between 0 and 24 inclusive. Values above 24 are invalid.
- The record is uniquely identified by its statistics date. Repeating the request updates the same daily record rather than creating a second one.
- Updating the record is intentional replacement, not accumulation.
- Overnight sleep-session attribution is deferred. This MVP stores a duration for the current statistics day.

Successful response — `200 OK`:

```json
{
  "date": "2026-10-24",
  "timezone": "Asia/Ho_Chi_Minh",
  "sleepHours": 7.5
}
```

## 6. Steps

### `POST /api/steps/batch`

Accepts raw step-increment events from the Go producer. The producer sends increments, not a precomputed cumulative total.

Request:

```json
{
  "runId": "demo-run-001",
  "events": [
    {
      "eventId": "demo-run-001-0001",
      "occurredAt": "2026-10-24T02:00:00Z",
      "stepsDelta": 12
    },
    {
      "eventId": "demo-run-001-0002",
      "occurredAt": "2026-10-24T02:00:10Z",
      "stepsDelta": 8
    }
  ]
}
```

Rules:

- `runId` identifies a producer run and is useful for demo diagnostics.
- `eventId` is generated when the producer creates an event. It must remain unchanged when that event is retried.
- `occurredAt` is when the simulated steps occurred.
- `stepsDelta` is a non-negative integer increment, not a cumulative snapshot.
- Store accepted raw events. Daily steps are calculated by summing unique accepted increments whose `occurredAt` falls within the local day.
- Duplicate `eventId` values must not increase the total. MongoDB uniqueness is the final guard against concurrent duplicate inserts.

Successful response — `202 Accepted`:

```json
{
  "runId": "demo-run-001",
  "received": 2,
  "accepted": 2,
  "duplicates": 0
}
```

Counts describe this submission. Retrying a previously accepted batch may return `accepted: 0` and a positive `duplicates` count.

## 7. Heart Rate

### `POST /api/heart-rate/batch`

Accepts raw heart-rate observations from the Go producer.

Request:

```json
{
  "runId": "demo-run-001",
  "events": [
    {
      "eventId": "demo-run-001-hr-0001",
      "occurredAt": "2026-10-24T02:00:00Z",
      "heartRateBpm": 92
    },
    {
      "eventId": "demo-run-001-hr-0002",
      "occurredAt": "2026-10-24T02:00:05Z",
      "heartRateBpm": 98
    }
  ]
}
```

Rules:

- Use the same event identity, retry, timestamp, and duplicate-handling rules as step events.
- `heartRateBpm` is a raw measurement in beats per minute. Validate that it is a plausible positive value; the demo may use a bounded range such as 20–250 bpm.
- Store accepted observations. Do not sum heart-rate measurements.
- The dashboard uses the observation with the latest `occurredAt` within the local day.
- If two observations have the same timestamp, use a deterministic tie-breaker such as event ID.

Successful response — `202 Accepted`:

```json
{
  "runId": "demo-run-001",
  "received": 2,
  "accepted": 2,
  "duplicates": 0
}
```

## 8. Duplicate and Error Handling

### Event identity

- The producer creates a unique `eventId` for every raw event.
- The mobile client creates an `intakeId` for every water-intake action.
- Retrying the same logical event/action must reuse its ID.
- The backend must enforce uniqueness in persistence, not rely only on a check-then-insert query.
- For this demo, per-record IDs are the primary idempotency mechanism. A separate HTTP `Idempotency-Key` header for whole requests is deferred.

### Error response

Use a consistent error shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request payload is invalid."
  }
}
```

Use `400 Bad Request` for invalid payloads and `500 Internal Server Error` for unexpected failures. Duplicate records should be handled according to the endpoint's duplicate behavior, not treated as newly created data.

## 9. Demo Acceptance Checks

- [ ] Health check returns `200 OK` through Nginx.
- [ ] Dashboard reads all four metrics in one request and returns `null` for missing metrics.
- [ ] Water intake creates separate records and sums them for the day.
- [ ] Sleep upserts one record for the current local day.
- [ ] Steps endpoint accepts raw increments and calculates daily totals without counting duplicate events twice.
- [ ] Heart-rate endpoint stores individual observations and dashboard chooses the latest one by event time.
- [ ] Producer and mobile retries reuse stable record IDs.
- [ ] MongoDB unique indexes prevent concurrent duplicate inserts.
- [ ] Daily boundaries use `Asia/Ho_Chi_Minh`, starting at 00:00.
- [ ] Raw event timestamps are preserved independently of server receipt time.
- [ ] Expo displays the dashboard and can submit sleep/water inputs.

## 10. Explicitly Deferred

Authentication, user-specific data isolation, historical-date query parameters, personalized daily cutoff times, overnight sleep-session attribution, HTTP-level idempotency keys, pagination, asynchronous processing, advanced analytics, and production-grade rate limiting are outside this local demo contract. Revisit them before a real multi-user deployment.
